### 1.2 Migrations

Every migration is a read-time rule or a one-time write on first load, never a rewrite of attacks. Each is listed with what happens if it is skipped.

- **M1 form from unit.** Read-time: `formOf(med)` returns `med.form`, else maps `unitLabel` (empty, tablet → Tablet; capsule → Capsule; spray, puff → Nasal spray; injection → Injection; anything else, such as sachet, → that text as the own form). Written on the next save of that medicine. Skipped: every old medicine opens in Edit with no form selected.
- **M2 guides object.** Read-time: a stored object without `guides` is `guides: {}`. No write. Old app versions ignore the extra key and the new column.
- **M3 per-medicine limits into guides. One-time write, once, in commit 0b (not 0a), because that is the commit where `guides` starts to be read.** For each type with at least one medicine carrying `maxDaysPerMonth` that **differs from the guideline**: set `guides[type]` to the **lowest** such value (warns earlier, the direction the app already prefers). A value equal to the guideline writes nothing (pre-filled, Q2). A medicine with no type keeps its number inert and is listed in the console report. The migration logs what it wrote. **Gate (June, Q3): before M3 is written I read her actual `hd_medications` from an Export backup she gives me**, run the rule on it by script, and show her the result: which medicines carry a limit, which types they would set, same-name pairs, and untyped medicines. M3 is not coded until she has seen that. Skipped: Treo's 10 reverts to the class number (the same, today) and any lower label limit is lost.
- **M4 `stoppedAt` is absent on all old records.** Nothing to migrate. Every existing medicine is in use.
- **No migration of attacks.** `medId` is new-writes-only. Old doses match by name.

Sync: whole-list last-write-wins on `medications_updated_at`, as now. A device that has not updated pushes `medications` without `medication_guides` and stamps a newer time, which would drop the guides from the winning copy. **Mitigation:** the new build merges field by field on pull (take remote `guides` when the local has none) and never pushes `guides: undefined` over a remote value. ### 1.3 Logic

- **Guides.** One function, `guideFor(type, guides)`, in `medGuardrails.ts`: stored number, else the guideline number (Q2). It replaces `mohDaysFor` for everything but an untyped drug's own fallback. Callers to move: `TodaySummary` (class bars, warnings, mixed line; its per-drug "own limit" branch goes), `MedicationInsights`, `COUNTED_CLASSES` in `medClasses.ts` (limit now comes from guides). `MOH_DAYS_*` constants stay as the guideline numbers.
- **"Any attack medicine".** Is the mixed-use line (`MOH_DAYS_MIXED`, 10), now with its own editable guide. `classDaysInWindow().any` changes to include untyped drugs (Q6), so `untyped` leaves the "counted in no bar" list. Gepants stay out (Q6).
- **Which types appear in the guides list.** Only types she has a medicine for, plus Any (15e). A stopped medicine still counts for its type here only while it has doses in the window; the row's listing follows medicines in use.
- **Type change recounts on Save.** [certain, from the code] A dose's class is looked up from the library by name at count time (`classOf`), and snapshots store no class. So changing the type needs **no write to any attack**: every past day recounts the moment the library saves, in Today and Insights. The work is the warning text in 16e: `daysTakenOf(med, attacks)` (distinct local days with a dose of that medicine, matched by `medId`, else name) gives "all 6 days". The type is staged in the form and written on Save only (15f rule: sub-screens stage, Save commits).
- **Stop using.** Sets `stoppedAt`. The medicine stays in the library so history keeps its type and its name. It leaves: the wizard chips and the voice-parse correction list (`recentMeds`). **`recentMeds` also scans attack history for names, which would bring a stopped medicine straight back into the chips.** The history half must skip names whose library entry is stopped. It stays in: all counts, Attack detail, Insights. Acts at once, no confirm, with Undo.
- **Delete, never logged.** Removes the library entry. "Never logged" means no snapshot matches its `medId`, or its name when it has no id use. Confirm sheet, then removal, then Undo toast.
- **Delete with its doses.** Per Q5. Steps: collect every affected `{attackId, snapshotTime, medication}`; set `medication: null` on those snapshots; stamp each touched attack's `updatedAt`; remove the library entry; hand all of it to the undo record. Impact line "Removed from 5 attacks. Insights and your report change for Aug to Oct" comes from `doseImpact(med, attacks)` (attack count, month span from the first to last affected snapshot). Confirm is two steps: remove sheet (17c), then dialog (17c-2). Which surface draws them is Gap 6, still open.
- **Recovery copy (Q5, written first).** Before any snapshot is touched, the app writes a record to **`hd_med_delete_recovery`** in `localStorage`, and only then edits the attacks: `{ id, deletedAt, medication, restores: [{ attackId, snapshotTime, medication }] }`. The copy is written for every delete, logged or not, so the whole library entry is recoverable too. If the write fails (storage full), the delete does not proceed and says so. It is a plain array, newest last, one record per delete.
  - **Where it lives:** this device only. It is **not synced** (no `user_prefs` column), the same reasoning as `hd_hit6_dismissed`: it is a safety copy for this phone, and syncing a copy of data the person chose to delete would keep that data on the server. It **does** travel in Export backup, because `backup.ts` writes every `hd_` key, which is the "by hand" route: export, read the record, restore.
  - **How long it is kept:** proposal, **30 days from `deletedAt`**, pruned on app start and on each new delete. Her call; shorter is less retained data, longer is more room to notice. It outlives the toast on purpose. It holds medicine names and dose text she asked to remove, so the retention is **stated in the delete confirm itself** (17c-2 for a medicine with doses, 17a-2 for one never logged), as one plain line under the impact line: that a copy is kept on this phone for 30 days so the delete can be recovered, then removed. **Not in Settings → Data**: that is screen 37, which this plan does not touch. Wording hers; the line is added when commit 4 builds the confirm, and the confirm's frames need that line drawn.
  - **Recovery by hand, no screen:** a short written procedure in `docs/` (read the key from an export, or from the web inspector on the phone, put `restores[].medication` back onto the matching snapshot by `attackId` and `snapshotTime`, re-add the medicine). It is checked once by following it on a seeded local copy. A recovery screen is not built and is not in this plan.
  - **Undo from the toast** uses the in-memory record, and removes the recovery record once it succeeds (the delete did not stand). A delete that stands keeps its record until it ages out.
- **"Logged at least once".** One predicate, `isLogged(med, attacks)`, used by the trash (17a vs 17b) and the impact line, so the two cannot disagree.
- **No longer used.** The overview section lists stopped medicines: letter badge, name, "Stopped {date} · {n} doses in your diary".
- **Free-text strength.** Stored as typed, trimmed. Required in the add wizard (Next disabled until a form and a strength exist). `parseStrength` accepts `^\d+(\.\d+)?\s*(mg|mcg|µg|g|ml|IU)$` only; anything else (combination, liquid concentration) shows the count with no total and the line "Lidd can't work out totals for this strength. Counts still work." Never guessed, in the same spirit as `doseUnits`: it must never turn "500/50 mg" into 500 or 50.
- **A new strength applies from today.** Past doses keep their own text because the dose is copied into each snapshot [certain]. No work, but the copy on 16c has to stay true, so a test checks it.
- **Max in 24 hours.** Stays `maxPerDay`, in units. The mg figure beside it is display only, `quantity × strength` when parseable. `checkDose` is unchanged and still never blocks a save.
- **Time between doses.** `minHoursBetween`, 0.5 steps. Existing whole-hour values are valid.
- **Usual dose above max warning (15c-4).** `usualDoseExceedsMax(quantity, maxPerDay)` returns the two numbers. It renders as an inline notice, blocks nothing, and the Add button stays enabled.
- **Undo, after add and after delete (item 182, option A).** In memory only, in `App`, one record at a time: `{ kind: 'add' | 'stop' | 'delete' | 'delete-with-doses', medication, snapshotRestores[] }`. The write happens immediately (so Today and Insights are right at once) and Undo writes the saved copy back. Consequences to accept: (1) a new toast replaces the record, so only the latest action is undoable; (2) if the app is killed inside the window, Undo is gone (the write was already made, the safe direction for add and stop, the unsafe one for a delete the person regrets; the confirm steps are what protect that case); (3) the package toast already pauses when the page is hidden, so backgrounding does not eat the window. Undo of a delete-with-doses re-stamps the touched attacks, so the restore wins the last-write-wins merge against the delete it reverses.
- **Retired list.** Unchanged. `isRetired` still hides junk names from counts; a deleted medicine is not "retired". They are different mechanisms and both stay.

Two looks: amber (a caution: "Usual dose (3) is more than the max in 24 hours (2)", "Check it fits the nasal spray") and info ("Lidd can't work out totals", "Counted under Any"). The kind is told apart by an icon and the words, never colour alone. Text 4.5:1 on its own surface, icon 3:1, in every theme. It wraps at 150% and 200%, nothing clipped. It is announced politely when it appears and moves no focus. Not a toast (it must persist) and not a dialog (it asks for nothing). A link inside is allowed only as a real button ("Edit it instead", 15a-2).
- **Package today.** None [certain: no notice in the component list]. The TextField hint/error is attached to a field only.

- **Uses in this plan:** 15a-2, 15b-2, 15c-4, 15f-2 (the strength flag), the 16e recount line, the Medications "Monthly guides" subtitle. That is more than 5, which is her bar for a part.

### Gap 2. Generic stepper

Used for usual dose, max in 24 hours, time between doses and the guide sheets. ### Gap 3. Toast with an Undo action and a pause

- **Requirement.** After add, stop and delete, a message with one Undo button that lasts about 10 seconds and **pauses while it is touched or has focus** (items 181, 182, 184). A person using VoiceOver or a switch must be able to reach Undo, and it must not disappear under their finger. Undo works with the keyboard, runs once, and the toast closes after it. The text is announced politely, once, with the action named ("Sumatriptan added. Undo"). It does not steal focus.
- **Package today, and the conflict.** The package `Toast` is message only by requirement: "No button, link or field inside it", `aria-hidden`, `pointer-events: none`, never takes focus, at least 5 seconds [certain, `ToastHost` and the Toast requirement text]. That rule exists for WCAG 2.2.1, because anything that needs the person to act must not vanish on a timer. An Undo button breaks every line of it. So this is not a prop on the existing component; the requirement text itself has to change or a second component is needed.
- **Two options, both need her.** (A) Extend `Toast` with `action` and a pause, and rewrite the "message only" requirement with the reason it changes (the undo is a safety net for a destructive action, not a required step). The visible toast then holds one focusable button and cannot be `aria-hidden`. (B) A separate component for "status with an action", leaving `Toast` as it is. Recommend B: the two have opposite focus, pointer and announcement rules, and a prop that flips all three is a trap. Also needed for either: where it sits when the keyboard is up (it already avoids the control in use) and 200% text.
- **Sizes that need roles.** The Undo button target (44pt), its gap from the message, and the new duration constant (10 s). The Undo label colour in the frame is `#3f5446` with "no token" [certain, design token list]: it must become a role and be contrast-checked, never copied as hex.
- **Who is touched while it shows.** The toast has to sit above `AppRoot`'s hidden layers (it is outside them already), and Undo must not be inert while a Sheet is open, because the undo toast after Delete appears right after the edit sheet closes.

## 4. The keyboard: Save and Next above the keyboard, field never hidden

This is the per-flow override June accepted on 2026-11-17 [certain, `decisions.md`]. Nothing was built for it, so the numbers below are plans.

**What is true now** [certain]: `capacitor.config.ts` sets `Keyboard.resize: 'native'`. The plugin shortens the web view, so the frame and the Sheet's footer end where the keyboard begins, but only after the keyboard animation plus 0.2 s. That delay is the "Save slide". With `'none'` the web view is not shortened, `innerHeight` and `visualViewport` do not move, and a low field is covered (rejected on her phone, 2026-11-16). On the web (browser, installed PWA) none of this applies: `AppRoot` follows the visual viewport directly with no slide.

**What the override must do.** In these three flows (add wizard, edit form and its Strength sub-screen, the guide and value sheets), the footer button is on screen **at the moment the keyboard appears**, sits directly above it, and the scrolling body keeps the focused field visible above the button.

**How I plan to build it**, in the order I would try, each measured before the next:
1. **Spike first, on the phone, before any flow code.** A throwaway probe page on this branch measuring, with the keyboard raised: time from keyboard visible to footer visible, `innerHeight`, `visualViewport`, frame height, for (a) `'native'` as now, (b) `'body'`, (c) `'none'` with the plugin's `keyboardWillShow` event giving the height. The existing probe (`VITE_VIEWPORT_PROBE`) is the model. I do not know whether (b) fires early enough [guessing]; the spike answers it.
2. **Expected winner: (c).** On entering one of these flows call `Keyboard.setResizeMode({ mode: 'none' })`, and put it back to `'native'` on leaving, even on an error or an unmount (the plugin has this call, seen in `Keyboard.m`, untried in Lidd [guessing it is reliable]). A hook `useKeyboardInset()` reads `keyboardWillShow` and `keyboardWillHide` (they fire at the start of the animation, so there is no one-second wait) and writes the height to a CSS custom property on the Sheet's frame. The Sheet's footer and body bottom padding use that property, so the footer rises with the keyboard and the body scroll area ends above it. The focused field is scrolled to the middle of the body, which the package Sheet already does for text fields (`centerInBody`) [certain]. Text field heights at the smaller visible area are checked at 200%.
3. **Where it lives.** The mode switch and the hook are Lidd's (`src/utils/keyboardOverride.ts`). The part that cannot be Lidd's is the Sheet reading an inset variable for its footer: that is a package change ("a Sheet footer and body can be offset by `--keyboard-inset`"). It is recorded as a gap and, per her rule, not worked around by editing Lidd's copy of a package part. Until it exists, I can build the hook and run the spike but not the footer lift.
4. **The web path** keeps its current behaviour (no plugin, no override), which already puts the footer above the keyboard through `AppRoot`'s visual-viewport frame.
5. **Rollback condition.** If the measured slide with `'none'` + `keyboardWillShow` is no better than `'native'`, or focus handling regresses, the flows stay on `'native'` and the slide is reported back to her as measured, with numbers.

**Checks on the phone** (native build, none run yet): keyboard up on Name (15a-3), on the own-form field (15b-3), on Strength (15b-4, 16c), on a guide or value sheet; the footer is visible with no delay and not under the keyboard; the focused field is not under the footer; rotate and the bar toggle (`setAccessoryBarVisible`) still behave; after leaving the flow the next screen's keyboard behaves as before (resize mode restored); a cold launch straight into the flow.
